# Challenge release image acceptance Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce a preserved, immutable Stage 1 release image and prove its challenge signing, configuration rejection, consent and activation hold against owned isolated services.

**Architecture:** A dedicated, manually dispatched GitHub Actions job builds the normal release Dockerfile once, publishes a unique candidate tag to the existing GHCR package, resolves its digest, and runs that digest with disposable PostgreSQL, Redis and Nostr relay containers. An external Playwright client exercises HTTP, relay and browser behavior; it never serves Keycast code. A bounded runner owns isolation, readiness, evidence and cleanup, and emits acceptance only after every required assertion actually executes.

**Tech Stack:** Existing Docker/Buildx and GitHub Actions, Python standard library orchestration/tests, Bun/Playwright, pg, ws and nostr-tools from the existing E2E lockfile; unchanged Rust server permission implementation.

**Spec:** [Stage 1 release sequence](../../challenge-signing-policy.md#release-sequence), [deployment boundaries](../../DEPLOYMENT.md), and [vendored synthetic fixture provenance](../../../core/tests/fixtures/challenges/SOURCE.md). Source inspected at 56fe48548d9ebc85336983335fc47cb9ad224e04. This implements an existing release gate, not new challenge semantics.

## Global Constraints

- Stage 1 registers enforcement and display support while holding management creation. No global `challenges` preset, production grant, management enablement, consumer change or deployment is part of this work.
- `challenge_actions` configuration is exactly `{}`; configured permissions combine with existing AND semantics. Empty permission links deliberately remain unrestricted.
- Positive families are challenge definitions (31923), entries/withdrawals/results (1111), and contest include/exclude labels (1985). Signing-family permission does not establish organizer identity or lifecycle eligibility.
- The full resulting signed-record size is limited to 64 KiB. Preserve canonical fixtures, locked runtime dependencies, signed embedded snapshots and existing permission parsing.
- Use only generated synthetic accounts, keys and grants. No production database, KMS, secrets, relays, account metadata, real creator identifiers or campaign material.
- Build and test the identical immutable release image, including its web assets. A development web server, debug binary, handler-only test or rebuild of the same source is not equivalent evidence.
- Do not run cloudbuild.yaml, `bun run deploy`, or the existing build-test-push workflow as an acceptance command: both publishing workflows have deployment side effects and mutable tags.
- Local Docker is unavailable for this task. Do not restart it, change its global context, retry it repeatedly, or borrow existing local services. Use the new hosted runner only after implementation is reviewed and execution is authorized.
- No new credentials, IAM changes, public listeners, production writes or secret retrieval. Unavailable registry access or artifact promotion capability is a named dependency, never a reason to widen access.
- This document authorizes no remote execution. Its implementation delivers the acceptance mechanism; production rollout and Stage 2 retain separate authorization and review gates.

## Review Focus

- A stale tag or rebuilt artifact must not pass: compare registry digest, local image identity and running container image before and after the suite (Tasks 1 and 5).
- A valid HTTP status with an error result, wrong signer or changed signed fields must fail; a relay timeout is never a denial (Task 3).
- A warmed valid handler must not mask a malformed configuration test: obtain a fresh unused authorization before changing its permission, then make its first RPC request (Task 4).
- A healthy API with an unavailable relay must not pass; readiness includes a bounded relay round trip and real NIP46 connect (Tasks 1 and 3).
- Early exit, cancellation, missing tests and diagnostic leakage must fail safely without losing ownership of cleanup or exporting credentials (Tasks 1, 4 and 5).

## Two gates and one source tree

The mechanism PR is reviewed, checked and merged before the first release-candidate dispatch. Its PR gate is the pure Python/Bun contracts and discovery regression in a separate read-only PR workflow, plus the repository's relevant required checks and independent review. No registry login, package write, credentialed integration or deployment runs on PRs. An optional, separately authorized non-publishing rehearsal may load an image on an isolated runner; label it mechanism proof only, never release evidence. This plan does not require a rehearsal or the postmerge run before the mechanism PR can merge.

After that authorized merge, a separately authorized main-only dispatch builds and accepts the release candidate. Enforce `github.ref == 'refs/heads/main'` and `source_sha == github.sha == github.workflow_sha == checkout HEAD`. The workflow, runner, test-client Dockerfile, adapters, fixtures, normal release Dockerfile and build inputs all come from that single tree; no older image-source checkout or separate tooling checkout is supported. Record the equal SHAs, workflow path and source/fixture/build fingerprints. The first candidate necessarily includes the mechanism PR and **every intervening main change** since the audited source, not only the original Stage 1 commits. The release owner must review that source/configuration delta and explicitly reconcile audit evidence before authorizing production; neither blind audit reuse nor an automatic audit rerun is allowed.

A failing postmerge run blocks production acceptance. Fix defects through a focused reviewed main-targeting PR, then authorize a new main-SHA candidate and rerun the complete gate. No merge/rollout authority or acceptance waiver follows from this sequence.
